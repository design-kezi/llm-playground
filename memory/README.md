# memory/ — 기억저장 레이어

설계: `docs/20-memory-design.md`. 의존성: Node 22 내장(`node:sqlite`)만. ESM.

## 인터페이스 (채팅앱이 부름)
```js
import * as memory from '../../memory/index.js';
memory.init({ db, model, policy? });                    // 동기. 프로세스당 1회. memory_* 테이블 생성
await memory.retrieve({ user_id, conversation_id, query, budget_tokens })
  // → { text, items, dropped_item_ids, attempts, deep_search? }  (dropped = 예산에서 밀린 활성 아이템 id. 턴별 RETRIEVE 로그에도 남음)   평상시 attempts=[] (AI 호출 0). miss 신호 시 embed 호출 포함
await memory.update({ user_id, conversation_id, turn_no, messages, force?, reason? })
  // force:true → 게이트·주기 무관하게 반드시 추출 (stair 모드에서 창에서 밀려나는 묶음을 넘길 때)
  // messages[i].conversation_id (선택) → 이전 대화에서 이월된 턴이 묶음에 섞여 올 때(앱 stair 창 이월). 출처(source)는 그 대화·턴으로 기록되고,
  //   추출 입력에는 "[이전 대화 턴 N]" 으로 표시되며, 현재 대화의 last_extract_turn 계산에서 제외된다. 없으면 모두 conversation_id 의 턴으로 본다.
  // → { ops, gate_reasons, parsed_ok, attempts } 또는 { ops:[], skipped:'gate', attempts:[] }
await memory.consolidate({ user_id, conversation_id })   // /end 시 1회 → { ops, attempts } (에피소드 요약 + 중복 병합)
await memory.list({ user_id, include_superseded?, include_log? })
  // → { user_id, profile, items, episodes, ops_log? }
```
`attempts[]` 는 모델 레이어 attempt 형식 그대로이며 각 항목에 `tag`(extract | consolidate | embed)가 붙는다.

## 모델 레이어에 기대하는 것
- `complete({ tag, purpose:'extract'|'summary', conversation_id, turn_no, system:[{text,cache}], messages, max_tokens, temperature, response_format:'json' })` → `{ text, attempts }`
- `embed({ tag:'embed', conversation_id, turn_no, texts:[...] })` → `{ vectors:[number[]|Float32Array], attempts }` (없으면 키워드 검색만으로 동작)
- `estimateTokens(text)` → number (없으면 글자수/1.5)

## 호출 시점 조정 (`policy.js`)
`init({ policy: {...} })` 또는 환경변수 `MEMORY_EXTRACT_EVERY_TURNS`, `MEMORY_GATE_ENABLED`, `MEMORY_RETRIEVE_MODE`(every_turn|on_change), `MEMORY_DEEP_SEARCH`, `MEMORY_MAX_EPISODES`, `MEMORY_BUDGET_TOKENS`(설정 시 채팅앱이 넘기는 budget_tokens 보다 우선 — 벤치 실험용).

| 원인 | 수정 |
|---|---|
| 매 턴 "최근 6턴 전체"를 추출기에 보여 이미 저장한 정보를 다시 ADD(매운 음식 4번, 전시회 4번) → 항목·프롬프트·출력 모두 불어남 | 마지막 추출 이후 **새 턴만** + 문맥 1턴(`splitNewTurns`, 채팅앱이 messages 에 turn_no 제공). 캐릭터 발화는 160자로 잘라 넣음 |
| 기존 항목 최대 80개를 매번 프롬프트에 | 새 턴과 키워드가 겹치는 것 우선 상위 20개(`relevantItems`) |
| 출력 잘림(max_tokens) → 같은 입력 재시도 → 또 잘림 | 잘리면 max_tokens 2배 + "짧게" 접미사로 재시도. 압축 JSON, 턴당 2개 이내 |
| stair 6턴 묶음을 한 번에 추출 → 잘림이면 묶음 전체 손실 | 3턴씩 나눠 순차 추출(`extractChunkTurns`), 뒤 조각은 앞 조각 결과를 기존 항목으로 봄 |
| 종료 요약 입력 9,271토큰, 출력 잘림 → 에피소드 없음 | 캐릭터 발화 80자, 대화 부분 2,500토큰 상한, 잘려도 episode 문자열은 건짐 |
| 깊은 검색이 옛 원문("이름은 하늘이야")을 꺼내 캐릭터가 옛 값을 말하고 추출기가 옛 값으로 되돌림 | 이미 항목으로 추출된 턴은 발췌 제외. 발췌는 "당시 발언" 표시, 추출기에는 UPDATE 금지 |
| 캐릭터가 사용자에게 한 약속(라떼아트)이 저장되지 않음 | 추출 규칙에 캐릭터 약속 명시(구체적 행동만) |

수정 후(응답 포함 전체, Haiku 5.5, 캐시 없는 단독 실행):

| 모드 | 전체 원/턴 | 추출 원/턴 | 추출 호출 | 잘림 | probe 자동판정 |
|---|---|---|---|---|---|
| slide (매 턴 update) | 0.58 | 0.21 | 35/40턴 | 0 | 9/11 PASS (+판사 5) |
| stair (6턴마다 묶음) | 0.47 | 0.09 | 12회(각 2조각) | 0 | 10/11 PASS (+판사 5) |

앱 경로 재측정에서 stair 추출이 비어 있던 원인 2개를 추가 수정: ① 앱 stair 는 현재 턴보다 뒤처진 묶음(18턴에 7~12턴)을 넘기는데 "마지막 추출 턴" 필터가 이를 전부 걸러냄 → force 묶음은 필터 없이 전부 새 턴 ② 텍스트는 같고 날짜(when)만 바뀐 UPDATE 를 "변화 없음"으로 버림 → when 비교 추가, when 없는 UPDATE 는 옛 날짜 상속. 앱과 같은 뒤처진 묶음으로 다시 돌린 stair: 추출 10회, 수정 정보 모두 반영, 0.41원/턴.

## 실측 3 (2026-10-22, 모델 세션 앱 경유 stair 재측정 피드백: 정리 턴 0.998원)

모델 세션의 앱 경유 stair 측정은 3대본 기억 문항 만점, 0.26~0.28원/턴이었지만 첫 정리 턴(12턴)이 0.998원이었다. 구성: 응답 0.16 + 추출 1조각 0.51(시스템 프롬프트 1,490토큰 캐시 쓰기) + 2조각 0.30 + 임베딩 0.02. 점검하며 찾은 것과 수정:

| 발견 | 수정 |
|---|---|
| 토큰 추정(글자수/1.5)이 한국어를 35~45% 과소 추정. 시스템 프롬프트 추정 1,093 → 실제 1,488. 그래서 "기억 블록 400토큰"은 실제 ≈650토큰, 종료 요약 입력 상한 2,500은 실제 4,863까지 들어갔다 | `tokens.js`: Anthropic count_tokens 로 보정(한글 음절 1.45 + 그 외 문자 0.4, 오차 ≤6%). 기억 레이어의 모든 예산이 실제 토큰 기준이 됨 |
| 추출 시스템 프롬프트 1,488토큰 | 규칙 압축 1,264토큰(캐시 쓰기 0.26 → 0.22원). 항목 길이 40자 → 30자 안팎(출력·블록 모두 절감) |
| 블록 선별이 `when_text` 를 보지 않아 "다음 주 화요일에 뭐 하기로 했지?"에 (다음 주 화요일) 취소 사건이 예산에서 밀림 | 시점 키워드 포함, 약속을 묻는 질의("해주기로 한 거")는 약속 항목 가중 |
| 추출 입력의 절반이 캐릭터 발화 | 약속·제안 신호(`gate.CHAR_PROMISE`)가 있는 줄만 160자, 나머지 90자, 문맥 턴 60자 |
| 캐릭터 약속 문장이 다른 턴 내용과 섞임(1회), 날짜 변경 UPDATE 가 중복 ADD 로 들어감(1회) | 규칙 3("행동 하나에 항목 하나"), 규칙 6("날짜·장소·이름 변경은 그 id 의 UPDATE") 명시. 비결정성이라 재발 가능성은 남음 |

추정기 보정의 부작용: 예산 400을 그대로 두면 블록에 항목이 5~7개만 들어가 probe 8/11(yuna). **같은 내용을 유지하려면 채팅앱 memory_budget_tokens 를 400 → 650 으로**(블록은 캐시된 시스템 블록이라 응답 비용 변화는 거의 없다). 650 기준 재측정(run-bench-direct stair, 응답 캐시 없는 단독 실행):

| 대본 | 전체 원/턴 | 추출 원/턴 | 정리 턴 추출 비용(12/18/24/30/36) | probe |
|---|---|---|---|---|
| yuna-40 | 0.40 | 0.077 | 0.71 / 0.64 / 0.75 / 0.53 / 0.44 | 11/11 (+판사 5) |
| kang-40 | 0.35 | 0.066 | 0.53 / 0.56 / 0.67 / 0.47 / 0.41 | 11/11 (+판사 5) |

> **정정(2026-10-23):** 위 "11/11" 은 앱 동작을 재현한 수치가 아니다. `run-bench-direct.mjs` 는 stair 모드에서도 매 턴 `retrieve` 를 확인 질문의 질의로 호출하지만, 앱은 정리 턴에 만든 블록을 6턴 동안 재사용한다. 그래서 앱 경유 v4/v5 에서는 같은 대본의 kang 4~5문항, yuna 1문항이 예산에서 밀린 항목 때문에 "기억 없음"으로 실패했다(실측 4). 단독 벤치 수치는 추출 비용·잘림 확인용으로만 쓰고, 기억 점수의 공식 수치는 앱 경유 벤치만 쓴다.

정리 턴 추출(2조각)은 0.4~0.75원이라 앱 경유에서는 응답 0.16을 더해 최대 ≈0.9원. 기억 쪽 절감은 10% 수준이고, 정리 턴의 최고치를 확실히 낮추는 방법은 **앱이 6턴마다 6턴을 넘기는 대신 3턴마다 3턴을 넘겨 조각을 1개로** 만드는 것(캐시 접두사 재작성이 2배 잦아지지만 창이 짧아져 상쇄). 과제 기준은 턴당 평균 1원이므로 현재도 충족하지만, 최고치 여유는 채팅앱 쪽 결정 사항으로 남긴다.

`MEMORY_BUDGET_TOKENS=650 node scripts/run-bench-direct.mjs model/bench/scenarios/kang-40.json stair` 로 재현. 디버그 입력/출력은 `MEMORY_DEBUG=<path>`.

**추가(모델 세션 앱 경유 v4, kang 34턴 옛정보 1건):** ops_log 로 확인한 원인은 블록 예산. 24·30턴 정리 때 "볼링 모임이 취소됐다"(UPDATE 결과, importance 2)가 예산에서 밀리고, 딸린 약속 "캐릭터는 볼링 모임 참석 여부를 확인해 보기로 했다"는 남아 캐릭터가 옛 계획을 말했다. stair 는 정리 시점의 블록을 6턴 동안 재사용하므로 질의 겹침으로는 못 구한다. 수정: ① 정정으로 생긴 활성 항목(옛 항목을 대체한 것, `store.correctedIds`)은 선별 점수 +4 — 바뀐 현재 값이 빠지면 남은 옛 맥락으로 옛 값을 추론하기 때문 ② 추출 규칙 6에 "사건이 취소되면 딸린 약속도 UPDATE". 프롬프트 1,305토큰.

**임베딩 한도 초과 대응(2026-10-24, nc9 중단 분석):** Gemini 임베딩이 429(분 단위 한도, 약 5분간)를 내는 동안 retrieve 의 깊은 검색은 예외를 잡아 키워드 방식(method "keyword(embed failed)")으로 대체되고 블록은 정상 생성됐다(nc9 3런 36턴: 포함 항목 11~14개, 응답 정답, 실패 호출 비용 0). update 는 항목 임베딩이 꺼져 있어 무영향. 다만 모델 레이어의 3회 재시도로 그 턴 지연이 6.8~9.0초였다 → 429/quota 실패 뒤 2분간 임베딩 시도를 생략하는 쿨다운(policy.embedCooldownMs, method "keyword(embed cooldown)") 추가. 테스트 57개.

**nc9·nc10 (2026-10-24, 임베딩 429 로 중단 — 비공식 런에서 확인한 것):** 회귀 1(9·10턴 약속·사건 누락)은 해소(backend·naruto 모두 저장). 새로 드러난 것 둘, 둘 다 "추측해서 고치기"였다.
- UPDATE_RETARGET 이 무관한 사실을 덮음: 모델이 12턴 "수영 다닌다"를 user.health 로 저장하고 17턴 "수영을 그만뒀다"를 user.routine + 그 id 로 보냄 → 구조 불일치 → "user.routine 활성 항목이 하나뿐"(7턴 한강 자전거)이라는 이유로 그쪽을 덮었다. 재지정은 단일값 속성에서만 하고, 모델이 closed 와 같은 entity 로 명시한 UPDATE 는 속성 라벨이 달라도 그 id 를 닫는다(추측이 아니라 명시).
- 단일값 변환이 모델 slot 오류를 증폭: 19턴 "우리 팀 신입은 QA팀 출신"을 user.job/user 로 보내 5턴 "데이터팀" 사실을 덮었다(35턴 unknown). job 을 단일값에서 제외(단일값 = name·age·location·diet).

## v2 — 임베딩 기반 장기 기억 (2026-11-01, docs/21)
사용자 결정: "A(서버 안 공개 임베딩 모델)로 진행, 퀄리티 좋은 것". 비교(docs/21 §2)로 **bge-m3 int8**(Xenova/bge-m3, q8) 선택. `policy.memoryMode`(`MEMORY_MODE`) 가 `v2`(기본) 이면 아래 경로, `v1` 이면 이전 동작(전부 주입·bigram 보충·miss 신호 깊은 검색).

- **임베더**(embed.js): `MEMORY_EMBED=auto|local|model|off`. local = @huggingface/transformers(onnxruntime CPU), 모델 파일은 `MEMORY_MODEL_DIR`(기본 ~/.cache/lite-memory/models, 0.57GB, 첫 기동 1회 다운로드, 이후 로드 0.7초). API 비용 0, attempts 에 `cpu_ms`(자체 호스팅 추론 비용 근거). 저장 벡터에는 `embed_model` 이 붙고 다르면 재임베딩 대상(`scripts/reindex.mjs`, 호출마다 `reindexPerCall` 개씩 점진 채움).
- **저장**: 항목 ADD/UPDATE 때 임베딩 저장. 사용자 발화는 retrieve 때 임베딩해 `memory_message_embeddings` 에 저장(추가 호출 없음). promise·event 와 에피소드는 `character_id`(캐릭터별), 사실·선호·프로필은 NULL(공유). slot 은 고정 어휘 없이 모델 라벨을 소문자로 둔다(SINGLE_VALUED 규칙만 유지). 규칙 13: 내용 없는 고민·이유도 저장.
- **retrieve(고정부, 캐시 접두사, 예산 `fixedBudgetTokens` 800)**: 프로필, 에피소드(최근 2 전문 + 이전 3 한 줄), 이름 슬롯, 열린 약속·사건, 안전 사실(allergy·health·diet), 중요도 4+, 정정 결과, 최근 12턴 저장분. id 순, 바이트 결정적. 나머지는 `dropped_item_ids`.
- **recall(질문 보충, 사용자 메시지 뒤, `recallTokens` 200)**: 활성+보관 항목·에피소드를 발화 임베딩 코사인으로 상위 `recallTopK` 3, 하한 `recallThreshold` 0.45, 최고점에서 `recallMargin` 0.10 안쪽만. 시점 표현(dates.js `dateRangeFromQuery`)이 있으면 그 기간 먼저. 보관 항목이 뽑히면 UNARCHIVE. 되묻기 표현·시점 표현이 있을 때만 원문 발췌(전체 이력, 상한 없음, 보관 출처 허용, `excerptThreshold` 0.45). **async** 로 바뀌었다(앱은 `await`).
- **update(추출 입력)**: 이름 슬롯·열린 약속/사건 + 새 턴과 가까운 항목 상위 `extractSimilarK` 10(활성·보관) + 같은 entity + 최근순, 상한 25. UPDATE 대상이 보관 항목이면 UNARCHIVE 뒤 대체.
- **consolidate**: 에피소드에 character_id·임베딩. 중복 후보 = 이 대화에서 바뀐 항목 + 유사도 `dupThreshold` 0.80 이상 기존 항목.
- **보관**: 상한 80 유지, 순서 importance → last_seen_turn → use_count. 보관 항목은 보충·추출 입력·발췌 후보로 남는다.
- 임계값 보정(2026-11-01, 실제 런 항목 145문항 vs 잡담 212턴): 질문→항목 코사인이 0.44~0.70 에 몰려 절대 임계값으로는 되묻기와 잡담을 못 가른다(0.45: 근거 83%·잡담 99%, 0.55: 48%·53%). 그래서 하한+상위K+margin. 실제 토큰·정답은 docs/21 §6 측정으로.
