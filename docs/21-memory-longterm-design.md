사용자 지시(원문):

- "저 기억도 대화량이 쌓이면 조회나 업데이트에서 문제가 있을텐데? vector db도 아니고"
- "아니 저렇게 고정화된 모델로 어떻게 다 기억을해..."
- 결정: "A(서버 안에서 돌리는 공개 임베딩 모델)로 진행하되 퀄리티 좋은 것으로 해줘"

순서: ① 현재 상태(§1) → ② 임베딩 모델 비교(§2, 실측 완료) → ③ 설계(§3~§5) → ④ 구현 → ⑤ 단위 테스트 → ⑥ 측정(수정 전/후 같은 대본, §6). 코드는 과제메인이 수정 전 기준선을 돌린 뒤 고친다.

숫자는 실측(app/data/app.db, model/bench/out, scratchpad 비교 스크립트) 또는 코드에서 읽은 값이고, 계산값은 "계산"이라고 적었다.

## 1. 현재 상태 (memory/ 빌드 dc-R8ujBaL5bXQt6wTTuN, 테스트 58/58)

### 1.1 저장 구조 (schema.js)
| 테이블 | 내용 | 범위 키 |
|---|---|---|
| memory_profile | 슬롯 6종 name·nickname·job·location·age·relation, 값 1개씩 덮어쓰기 | user_id |
| memory_items | 원자 문장 1행. type fact/preference/event/promise, text, when_text, slot `<대상>.<속성>`(고정 어휘), entity, depends_on, value, status active/superseded/archived, importance 1~5, use_count, embedding(BLOB, 미사용), source(대화·턴) | user_id |

### 1.2 쓰기 (update, index.js:223~)
1. 앱 stair 창(12턴 차면 오래된 6턴을 넘김, 비동기)이 넘긴 6턴을 3턴 조각 2회로 추출 호출(deepseek-flash 추론 끔, 2026-11-01 변경 전 gemma-4-31B). /end 때 남은 창을 end_flush.
2. 추출 입력 = 프로필 + **기존 항목 최대 20개**(relevantItems index.js:669: 이름 슬롯·열린 사건/약속 고정 + 최근순) + 새 턴 + 오늘 날짜. 고정부 2,160토큰.
3. applyOp(index.js:354): UPDATE 는 모델이 준 id 가 **활성**이고 slot·entity 가 맞을 때만. 단일값 속성(name·age·location·diet)만 재지정·ADD→UPDATE 변환. 다중값 속성의 닫힘 없는 UPDATE 는 ADD 로 공존. 새 행 삽입 + 옛 행 superseded(삭제 없음). depends_on 닫기, 이름 전파.
4. 80개 초과 시 enforceCap(index.js:554): importance → use_count → id 순으로 archived.

### 1.3 읽기 (retrieve, 매 턴, AI 호출 없음)
1. buildBlock(index.js:83): 프로필 1줄 + 최근 에피소드 2건 + **활성 항목**. 예산(앱 기본 2000토큰) 안이면 전부, 넘치면 importance·최근성·열림·정정·이름 점수로 선별. 캐시 접두사.
2. recall(index.js:125): 블록에 못 들어간 활성 항목 중 글자 2개 묶음(bigram) 겹침 ≥2 인 것 최대 3줄, 사용자 메시지 뒤에만.
3. deepSearch(index.js:159): "기억 안 나?" 류 ko 정규식 신호 때만. 최근 200개 사용자 원문 중 이미 항목이 된 턴(status 무관) 제외 → 키워드 겹치는 60개를 Gemini 로 임베딩해 상위 3개 발췌. **임베딩이 쓰이는 유일한 곳.** Gemini 무료 등급 분당 한도(429)로 측정이 두 번 끊겨 이 범위로 묶어 두었다(docs/50 2026-11-01).

## 2. 임베딩 모델 비교 (2026-11-01 실측, 0원, scratchpad/embed-test: build-data.mjs → eval.mjs → latency.mjs)

### 2.1 전제
- 서버 안 실행: @huggingface/transformers 3.x(onnxruntime, CPU), Node 22. 이 맥(24GB)에서 측정. API 호출·한도 없음.
- 후보: Hugging Face 에 ONNX 변환이 있는 것만 — bge-m3, multilingual-e5-large/small, Qwen3-Embedding-0.6B. 한국어 특화 KURE-v1·BGE-m3-ko 는 ONNX 가 없어 제외(Python 변환 필요). 공개 리더보드(Korean-MTEB)에서 Qwen3-Embedding 8B/4B 가 1·4위, KURE-v1 6위, Qwen3-0.6B 11위, bge-m3 12위 — 큰 모델은 CPU 작은 서버에서 못 돌린다.
- 데이터: **A** 대본 12개(4캐릭터 × 120·40·revisit-40)의 확인 질문 220개 → 그 대본의 심기/수정 발화 전체에서 근거 턴 순위. **A2** 실제 런(lt2 v2-dsx 120턴 4개, dm2 revisit 4개)의 기억 항목 문장을 후보로 145문항. **B** 같은 사실 쌍(DB superseded 사슬 599쌍) vs 무관한 쌍(같은 사용자 활성 항목 무작위 600쌍) 유사도 분포. 지연: 실제 대본 문장(평균 28자), 따뜻한 상태 40회 중앙값.

### 2.3 실패 유형 (모델 공통, bge-m3 기준 A 실패 28건)
- 세상 지식이 필요한 암묵 질문 14건: "편의점 과일 컵 골라줘" → 복숭아 알레르기, "스트레스 뭐 하면 풀릴까" → 펌프. 암묵 유형 상위3 33~56%(전 모델).
- 내용 없이 시점만 있는 질문: "다음 달 초에 어디 가야 한다고 했지", "내일부터 뭐 달라진다고 했잖아".
- 막연한 약속 되묻기 5건: "너 나한테 뭐 해주기로 했어?"
- 이름 4건은 후보 집합 구성(filler 턴 제외)의 문제로 무효.
→ 임베딩이 아니라 설계로 받친다(§3.2): 알레르기·건강·식단과 열린 약속·사건은 검색과 무관하게 고정부에, 시점 질문은 날짜 범위 먼저. 나머지 사실·선호 되묻기는 전 모델 상위3 81~100%.

### 2.4 선택: **bge-m3 int8**
근거: 상위1·3 정확도 1위, fp16 과 같은 품질에 CPU·RSS 절반, 파일 0.57GB. Qwen3 fp32 는 같은 사실/무관 분리가 가장 좋지만 RSS 2.5GB·CPU 137ms 로 가장 무겁고, q8 로 줄이면 품질이 크게 떨어진다. e5-large 는 품질 동급이나 유사도 범위가 압축돼(.86~.96) 임계값 폭이 좁다. 차이는 1~2문항 수준(220문항에서 1문항 = 0.45%p)이라 "모델 간 품질 차이는 작고 운영 부담 차이가 크다"가 결론이다. 임계값은 §3.2.

### 2.5 자체 호스팅 임베딩 비용 (사용자 결정: CPU 사용량만 1원에 반영, 메모리 상주는 운영비)
- 턴당 호출: 조회 1회(사용자 발화) + 접기 때 새 항목 임베딩(활성 0.5개/턴 → 0.5회) ≈ 1.5회/턴. 묶음 16개 처리는 131ms 라 접기 때는 묶어서 한다.
- CPU 실측 59ms/문장 × 1.5 = 0.088 vCPU초/턴. Lightsail 2 vCPU·4GB $24/월 → 1 vCPU초 0.00648원 → **0.0006원/턴(계산)**. 리포트는 가정값 100ms/턴 ≈ 0.0007원/턴 [추정] 으로 적어도 상한이다.
- RSS 1.86GB/프로세스: 4GB 서버에서 Next 앱과 함께 1개 가능. 벤치 3레인 = 3프로세스 5.6GB(24GB 맥).

## 3. 설계안 v2 (임베딩 기반, 규모: 사용자당 수천 턴·항목 수천 개까지 같은 구조)

원칙: **들은 말은 버리지 않는다**(사용자 원문 전부 색인), **항목은 색인이자 현재값**(자유 문장, 라벨은 보조), **검색은 후보 선정, 판단은 모델**, **블록 고정부는 작게·바이트 결정적**(캐시), 질문에 따라 바뀌는 것은 사용자 메시지 뒤에.

### 3.1 저장
- memory_items: 그대로 + 변경
  - `character_id TEXT NULL` — promise·event 만 채움(사용자 사실·선호는 null = 공유).
  - `embedding BLOB` — 저장 시 bge-m3 int8 로 text 임베딩(1,024 × Float32 = 4KB). `embed_model TEXT` — 모델 식별자(바뀌면 전부 재임베딩).
  - `last_seen_turn INTEGER` — 사용자가 다시 언급해 조회·정정에 걸린 마지막 턴(보관 순서 근거).
  - slot/entity: **고정 어휘 폐지.** 추출기가 쓴 라벨을 그대로 둔다(정정 판단의 보조 정보). SINGLE_VALUED 규칙은 유지(이름·나이·거주지·식단).
- memory_message_embeddings: 사용자 발화마다 저장(매 턴 조회 임베딩을 그대로 저장하므로 추가 호출 0). `embed_model` 컬럼 추가. Gemini 3,072차원 옛 행은 모델 식별자 불일치로 폐기.
- memory_episodes: `character_id`, `embedding` 추가(요약도 검색 대상).
- 마이그레이션(init 1회, 멱등): 컬럼 추가, promise·event 행과 에피소드의 character_id 를 source_conversation_id → conversations.character_id 로 채움, embedding 없는 행은 백그라운드 재임베딩 명령(`memory/scripts/reindex.mjs`)으로 채움.
- 모델 파일: `MEMORY_MODEL_DIR` 캐시, 첫 기동 때 1회 다운로드(0.57GB). `MEMORY_EMBED=local|off`.

### 3.2 조회 (매 턴, AI 호출 0, 임베딩 1회 ≈ 10ms)
```
블록 고정부 (캐시 접두사, 예산 B_fixed 기본 800토큰, 기억이 안 바뀐 동안 바이트 동일)
  프로필 1줄
  에피소드: 최근 2건 요약 + 그 이전은 "날짜: 제목" 1줄씩(최대 5)
  고정 항목(id 순): 이름 슬롯, 열린 약속·사건(이 캐릭터 + 공유, 지난 날짜 제외), 안전 사실(allergy·health·diet 라벨 또는 importance ≥4), 정정 결과(corrected), 최근 12턴 안에 새로 저장·정정된 항목
질문 보충 (사용자 메시지 뒤, 예산 R 기본 300토큰, 턴마다 바뀜)
  q = 이번 발화 임베딩(저장도 함께)
  후보 = 이 사용자의 활성+보관 항목(character_id null 또는 같음) 중 고정부에 없는 것 + 에피소드
  시점 표현("지난달", "30일 전", "그때 11월 초")이 있으면 dates.js 로 범위를 뽑아 created_at/when_text 로 먼저 좁힘(없으면 전체)
  점수 = 코사인 유사도(+ 날짜 범위 안이면 +0.05). 상위 K=3, 하한 0.45, 최고점에서 0.10 안쪽만(보정 §7.1: 0.55 는 근거 항목 절반을 놓친다)
  동점은 id 오름차순(결정성). 보관 항목이 뽑히면 UNARCHIVE + last_seen_turn 갱신
  원문 발췌: 상위 항목의 유사도가 t_item 미만이거나 되묻기 신호가 있으면 memory_message_embeddings 전체에서 상위 3개 원문(이미 활성·대체 항목의 출처 턴은 제외, 보관 출처는 허용), +150토큰
```
- 지금의 deepSearch 정규식 신호·최근 200개 상한·키워드 60개 풀은 없앤다. 원문 검색은 매 턴 가능하되, 항목이 충분히 가까우면 생략(토큰 절약).
- 결정성: 고정부는 id 순·정수 비교만. 보충은 캐시 접두사 밖이라 흔들려도 캐시에 영향 없음. 상위 K 동점은 id 로 가른다.

### 3.3 업데이트 (추출 입력과 정정 대상)
- 추출 입력 항목 = 고정(이름 슬롯·열린 약속/사건) + **새 턴 묶음 임베딩과 가까운 항목 상위 10(활성·보관, 임계값 t_item)** + 그 항목들과 같은 entity 의 항목 + 최근순 채움, 상한 25.
- 추출기 프롬프트: 라벨 어휘 표 삭제(토큰 −약 150), "같은 대상의 같은 속성이면 UPDATE(id), 다른 대상·다른 속성이면 ADD, 내용을 밝히지 않은 고민·이유·비밀은 '…있다고 했으나 내용은 말하지 않았다'로 저장" 규칙(G8). 캐릭터 약속·사건은 character_id 를 코드가 채움.
- applyOp: UPDATE 대상이 archived 면 UNARCHIVE 뒤 대체. byId 불일치 시 재지정은 지금처럼 단일값 속성만. 다중값 공존 규칙(B51) 유지. 새 항목은 저장 즉시 임베딩(묶음).
- consolidate 입력 = 이 대화에서 ADD/UPDATE 된 항목 + 각각과 유사도 ≥ t_dup(기본 0.80, 같은 사실 쌍 p50 .76 근방·측정에서 조정)인 기존 항목 → 중복·모순 정리를 같은 호출에 포함(추가 호출 없음).

### 3.4 보관·잊기
- 상한 80 은 "고정부 후보 수" 상한이 아니라 **활성 상태 상한**으로 유지하되, 보관 항목은 §3.2 보충·§3.3 추출 입력·원문 검색의 후보로 **항상 남는다**(지금은 어디에도 없음). 되살리기 UNARCHIVE 로그.
- 보관 순서: importance → last_seen_turn 오래된 것 → use_count.
- superseded 는 그대로(되살리지 않음, 이력·옛 이름 금지어용). 시간 감쇠(N일 미언급 자동 보관)는 넣지 않음 — 측정 대본에 몇 달 뒤가 없어 효과를 재지 못하므로.

### 3.5 기억 범위 (사용자 결정 반영)
- 공유: 프로필, fact·preference 항목. 캐릭터별: promise·event 항목, 에피소드.
- 인터페이스: update·retrieve·recall·consolidate·list 에 선택 인자 `character_id`(앱은 이미 전달, 2026-11-01). 없으면 사용자 전체(이전 동작).
- 다른 캐릭터의 약속은 조회·보충·원문 발췌에 들어가지 않는다. 사용자 사실은 어느 캐릭터에서 말했든 들어간다.

### 3.6 바꾸지 않는 것
- 추출 시점(stair 접기·비동기), ops_log, 공개 인터페이스(인자 추가만), 프로필 슬롯, 다중값 공존 규칙, 출처(M4) 기록. 다국어(G11)는 범위 밖.

## 5. 단위 테스트 계획 (기존 58개 유지, 가짜 임베딩 모델로 결정성 확보)
1. 저장 시 항목·발화 임베딩이 BLOB 과 embed_model 로 남고, 모델 식별자가 다른 옛 벡터는 재임베딩 대상이 된다.
2. 보충: 글자가 안 겹치는 질문(가짜 임베딩에 "가까움" 지정)이 항목을 고르고, 고정부에 있는 항목은 중복 선택하지 않는다. 동점은 id 순.
3. 보관 항목이 보충에 뽑히면 UNARCHIVE 로그와 함께 활성이 되고 last_seen_turn 이 갱신된다.
4. 추출 입력: 활성 30개 중 최근순 20개 밖의 가까운 항목과 보관 항목이 포함되고 상한 25 를 넘지 않는다.
5. UPDATE 대상이 보관 항목이면 되살린 뒤 superseded 로 바뀐다.
6. 원문 검색: 200개 밖 오래된 발화가 임베딩으로 후보에 들고, 활성·대체 항목의 출처 턴은 제외되며 보관 출처는 허용된다.
7. 날짜 범위: "지난달에 말한 것" 질문이 created_at 범위로 후보를 좁힌다.
8. 기억 범위: character_id 가 다른 약속은 블록·보충에 안 들어가고 사용자 사실은 들어간다. 마이그레이션이 conversations.character_id 로 채운다(멱등).
9. 고정부 바이트 결정성: 같은 기억·같은 캐릭터 → 같은 블록 문자열.
10. 반쪽 발화 규칙: fake-model ops 로 저장 형태 검증(실모델 준수율은 §6 측정).
11. MEMORY_EMBED=off 면 임베딩 없이 지금 경로(bigram 보충)로 동작한다(폴백).
