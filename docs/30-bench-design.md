> 작성: 모델 세션. 상태: 설계안 v2(리뷰 반영, 미구현, 미실측). 숫자는 가정 단가 기준 추정.
> 제출 기한: 2026-10-31(토). 범위는 줄이지 않는다.

## 0. v2 변경 요약 (과제 요구사항 리뷰 반영)

## 3. 전체 구성

```
대본(JSON) ──┐
조건표(JSON) ─┼─▶ 벤치 실행기 ──HTTP──▶ 채팅앱 API ──▶ 기억저장 레이어
             │        │                     │                │
             │        │                     └──── 모델 레이어 ◀┘
             │        │                              │
             │        ▼                              ▼
             │   대화 기록 수집              호출별 usage (채팅앱 calls 테이블)
             │        │                              │
             │        └──────────────┬───────────────┘
             │                       ▼
             │      비용 집계 / 규칙 채점 / AI 판정 / 기억 채점
             ▼
사람 블라인드 판정(소량) ──▶ AI 판정 보정
```

- 벤치 위치: `model/bench/`. Node(ESM).
- 대화 진행: `POST /api/conversations` → `POST /api/conversations/:id/messages` 반복 → `POST /api/conversations/:id/end` → `GET /api/conversations/:id/report`.
- 기억 확인: `GET /api/memory?user=<이름>&include_superseded=1&include_log=1` 로 실제 저장된 기억과 연산 기록을 함께 수집한다. 응답이 틀렸을 때 "추출을 못 했나 / 꺼내지 못했나 / 꺼냈는데 응답이 안 썼나"를 나눠 볼 수 있다.
- 조건 전환: 조건마다 채팅앱을 해당 환경변수로 다시 띄운다. 실행은 순차.

### 3.1 조건을 바꾸는 환경변수

| 변수 | 소유 | 값 | 상태 |
|---|---|---|---|
| `MODEL_RESPONSE` / `MODEL_EXTRACT` | 모델 | 모델 ID | 모델 레이어에서 구현 |
| `MODEL_CACHE` | 모델 | `on` / `off` | 모델 레이어에서 구현 |
| `MODEL_REASONING` | 모델 | `off` / `minimal` / `default` | 모델 레이어에서 구현 |
| `APP_WINDOW_MODE` | 채팅앱 | `full` / `slide` / `stair` | **채팅앱에 요청** |
| `APP_RECENT_TURNS` / `APP_STAIR_MAX` | 채팅앱 | 6 / 12 | **채팅앱에 요청** |
| `APP_MEMORY` | 채팅앱 | `on` / `off` (대조군용) | **채팅앱에 요청** |
| `APP_CHARACTER_VARIANT` | 채팅앱 | `full` / `short` (시트 길이) | **채팅앱에 요청** |
| `APP_MAX_TOKENS` | 채팅앱 | 정수 | **채팅앱에 요청** |
| `MEMORY_EXTRACT_EVERY_TURNS`, `MEMORY_GATE_ENABLED`, `MEMORY_RETRIEVE_MODE`, `MEMORY_DEEP_SEARCH` | 기억저장 | 기존 | 구현됨 |
| `MEMORY_BUDGET_TOKENS` | 기억저장 | 정수 (기본 400, 앱이 넘기는 값보다 우선) | 구현됨 |
| `MEMORY_MAX_EPISODES` | 기억저장 | 정수 (기본 2) | 구현됨 |

- 리포트는 실행할 때의 환경변수 전체를 함께 저장해서, 어떤 설정으로 나온 숫자인지 재현할 수 있게 한다. 채팅앱 `GET /report` 의 `settings = { app, env }` 를 그대로 쓴다(대화 시작 시점 값).

### 3.2 실행 시 주의 (채팅앱·기억저장 세션 공유 사항)
- `APP_*` 값이 잘못되면 첫 요청부터 500. 서버를 띄운 뒤 `POST /api/conversations` 가 200인지로 확인한다.
- 재시작할 때 `next start` 만 끄면 `next-server` 자식 프로세스가 남아 옛 설정으로 응답한다. `next-server` 까지 종료하고 3000 포트가 빈 것을 확인한 뒤 띄운다.
- `stair` 모드는 정리 시점에만 retrieve/update 한다. 정리 묶음은 `update` 의 `force` 로 항상 추출된다(게이트 무시).
- `stair` 에서는 retrieve 가 정리 시점에만 불려서, 확인 질문 턴의 miss 신호 깊은 검색이 켜지지 않는다. 조건표·결과 해석에 "stair = 깊은 검색 사실상 off"로 적는다.
- `APP_CHARACTER_VARIANT=short` 는 캐릭터 시트의 `prompt_short` 가 있어야 동작한다(현재 없음 → 대화 시작 400). 비용 낮추기 실험 전에 압축판을 작성한다.

## 4. 대본 설계

### 4.1 기본 형태
- 정규 대본 3개 × 각 40턴. 캐릭터는 yuna / kang / sera를 하나씩.
- 턴 구간: 초반 1~13 / 중반 14~27 / 후반 28~40. 비용 리포트 구간과 같다.
- 사용자 메시지는 **어떤 응답이 와도 성립하게** 쓴다.
- 대본마다 사용자 이름을 실행 ID로 새로 만든다(`bench-<run_id>`). 기억이 실행끼리 섞이지 않게 한다.

### 4.2 메시지 종류

| 종류 | 역할 | 예 |
|---|---|---|
| 심기 | 기억할 정보를 처음 말함 | "나 고양이 하늘이 키워" |
| 수정 | 기존 정보를 바꿈 | "아 이름 구름이로 바꿨어" |
| 취소 | 약속·사실을 없앰 | "토요일 영화 취소하자" |
| 방해 | 수정처럼 보이지만 아님 | "친구네 고양이는 구름이래" |
| 채움 | 다른 주제로 거리 만들기 | 일상, 장면 전환, 감정 |
| 확인 | 기억을 시험 | "우리 고양이 이름 기억나?" |
| 함정 | 말한 적 없는 정보 질문 | "내 생일 언제였지?" |
| 암묵 | 묻지 않고 반영해야 함 | (매운 거 못 먹음 이후) "배고파, 뭐 먹지" |

### 4.3 기억 확인 질문 유형

| 유형 | LongMemEval 대응 | 대본당 개수 |
|---|---|---|
| 사용자 정보·선호 직접 회상 | 정보 추출 | 2 |
| 사용자가 한 약속 회상 | 정보 추출 | 1 |
| 캐릭터가 한 약속 회상 | 어시스턴트 발화 회상 | 1 |
| 수정·여러 번 수정 반영 | 정보 갱신 | 2 |
| 부분 수정 (날짜만 바뀜, 장소 유지) | 정보 갱신 | 1 |
| 취소 반영 | 정보 갱신 | 1 |
| 방해 정보에 덮어쓰지 않음 | (보강) | 1 |
| 두 정보 결합 | 여러 세션 추론 | 1 |
| 상대 시간 ("약속까지 며칠") | 시간 추론 | 1 |
| 말한 적 없는 정보 | 모름 | 2 |
| 반쯤 말한 정보 | 모름 | 1 |
| 암묵 반영 | (보강) | 2 |
| **합계** | | **16 × 3대본 = 48개** |

캐릭터 약속 회상은 대본이 캐릭터의 대사를 고정할 수 없으므로, 사용자가 "다음에 노래 불러줄 수 있어?"처럼 약속을 유도하고, 실제로 캐릭터가 약속했는지는 기록에서 확인한 뒤 채점한다(약속하지 않았으면 해당 문항은 제외하고 그 사실을 기록).

### 4.4 배치 규칙
- 확인 질문은 원천 발화로부터 **최소 13턴 뒤**. 계단식 창 최대 길이(12턴)를 넘겨야 최근 대화만으로는 답할 수 없다.
- 확인 질문 하나는 한 번만 묻는다.
- 함정 질문은 그럴듯한 것으로 고른다(생일, 품종, 직장 이름).

### 4.5 확인 질문 데이터 형식
```json
{
  "turn": 34,
  "kind": "probe",
  "type": "multi_update",
  "difficulty": "hard",
  "user": "근데 우리 고양이 이름 기억나?",
  "expect": ["하늘"],
  "stale": ["구름"],
  "forbidden": [],
  "source_turns": [3, 18, 27]
}
```
난이도: 거리(13~20턴 보통, 21턴 이상 어려움), 수정 횟수, 방해 정보, 결합 여부.

### 4.6 특수 대본 2개

| 대본 | 내용 | 목적 |
|---|---|---|
| **재방문** | 1차 대화 25턴(심기·수정) → `/end`로 종료 → 같은 사용자 이름으로 새 대화 15턴(확인·함정) | 대화 종료 정리(consolidate)와 대화 간 기억. 판단 질문 3의 "사용 패턴이 달라지면" |
| **장기 120턴** | 장면 10개(12턴씩)로 이어지는 고정 대본. 초반 정보를 최대 100턴 뒤에 확인 (`model/bench/scenarios/src/skeleton-120.mjs`) | 후반 비용이 평탄한지, 기억이 쌓일 때 기억 블록 예산(앱 설정 1000토큰, `app/lib/config.js`; 기억 레이어 자체 기본값 400은 앱이 넘기는 값에 밀림)을 넘으면 무엇이 빠지는지. 판단 질문 3 |

## 6. 실험 단계

### 6.1 단계 1: 1차 선별
- 정규 대본 1개 × 6개 모델, 계단식 + 캐시 켬 + 기억 켬.
- 탈락 기준: 규칙 위반(사용자 행동 확정, 언어 섞임)이 턴의 10% 초과, 또는 기억 점수가 대조군(기억 끔)보다 낮음.

### 6.2 단계 2: 정밀 비교
- 상위 3개 모델 × 창 3 × 캐시 2 × 정규 대본 3 × 반복 2 = 108회 + 대조군.
- AI 짝 판정과 사람 보정은 이 단계 결과로 한다.

### 6.3 단계 3: 비용 낮추기 실험 (최종 모델 1개)
한 번에 한 가지씩 줄이고, 품질·기억 점수가 언제 기준 아래로 떨어지는지 본다.

| 줄이는 것 | 단계 |
|---|---|
| 캐릭터 시트 | full → short |
| 기억 예산 | 400 → 250 → 150 토큰 |
| 계단식 창 | 12/6 → 8/4 |
| 최대 출력 | 200 → 120 |
| 추출 주기 | 6턴 → 9턴 |

결과는 "비용-품질 곡선"으로 보여 주고, 기준을 지키는 가장 싼 설정을 최종안으로 정한다. 판단 질문 2(무엇을 유지하고 무엇을 양보했나)의 근거가 된다.

### 6.4 단계 4: 최종 측정
- 최종 설정으로 정규 대본 3 × 반복 3 + 재방문 대본 + 장기 120턴 대본.
- 이 결과가 제출 보고서의 대표 숫자다.

## 7. 비용 측정 (Q1)

- 출처: 채팅앱 `calls` 테이블(호출별 attempt 기록). 실패·재시도 포함.
- 원화 = (미캐시 입력 × 입력가 + 캐시 읽기 × 캐시가 + 캐시 쓰기 × 쓰기가 + 출력 × 출력가) × 환율. 가격은 `model/pricing.json`(출처 URL·기준일·환율 기준일 포함).
- DeepSeek는 피크·비피크 둘 다 계산, 대표값은 피크.
- AI 판정 비용은 운영비가 아니므로 별도 합계.
- 리포트 항목: 평균, 구간별 평균, 최대 턴(어느 턴, 어떤 호출 때문인지), 캐시 적중률, 호출 종류별 비중(응답/추출/정리/임베딩/재시도), 대화 종료 정리 비용의 턴당 환산.
- **AI 외 운영비 (1원과 분리)**: 데모 3일 기준 로컬 서버 + SQLite + ngrok 무료/유료 플랜. 실서비스 가정(예: 일 1만 턴)일 때 서버·DB 월 비용 추정 한 줄.

## 8. 품질 채점 (Q2)

### 8.1 규칙 채점 (0원, 모든 턴)
| 지표 | 방법 |
|---|---|
| 사용자 행동·감정 확정 | "너는 ~했다/웃었다", "당신은 ~" 패턴 + 2인칭 동작 서술 |
| 반복 맞장구 | 연속 응답 간 3-gram 중복률, 질문·새 전개 포함 응답 비율 |
| 언어 섞임 | 한글 외 문자 비율 |
| 형식 이상 | 빈 응답, 설정 읊기, 메타 발언 |
| 길이 분포 | 참고용(점수 아님) |

### 8.2 AI 짝 판정
- 같은 대본, 같은 10턴 구간의 두 대화를 나란히 보여 주고 어느 쪽이 나은지 묻는다.
- 기준: ① 캐릭터 일관성 ② 맥락 적합성 ③ 대화 지속성 ④ 사용자 존중(행동·감정 대신 정하지 않음).
- 편향 완화: 순서 바꿔 두 번, 엇갈리면 무승부. 판정 모델은 서로 다른 회사 2개. "길이는 기준이 아니다" 명시.
- 출력: 축별 승/패/무 + 한 줄 이유(JSON). 집계: 승률, Bradley-Terry 점수.

### 8.3 사람 블라인드 보정
- 짝 20개를 모델명 가리고 사용자가 판정. AI 판정과 일치율 보고. 70% 미만이면 AI 판정은 참고용.

## 9. 기억 채점 (Q3)

| 결과 | 의미 | 점수 |
|---|---|---|
| 정답 | 최신 정보로 맞음 | +2 |
| 부분 | 일부만 맞음 | +1 |
| 모름 | 기억 안 난다며 되물음 | 0 (함정 질문에서는 +2) |
| 옛 정보 | 수정 전 정보 | −1 |
| 지어냄 | 대화에 없던 정보 | −2 |

- 1단계 규칙: `expect`/`stale`/`forbidden` 키워드. 애매하면 2단계.
- 2단계 AI 판정: 원천 발화, 질문, 응답을 주고 5개 중 하나 선택(JSON). 암묵 유형은 항상 2단계.
- 실패 원인 분류: `GET /api/memory?user=..&include_superseded=1&include_log=1` 로 나눈다.
  - (a) 추출 실패: 그 사실의 item이 없음. 그 턴에 extract 호출 자체가 없으면 게이트에 막힌 것(calls 테이블로 확인).
  - (b) 예산에서 밀림: item은 있는데 확인 턴의 `op='RETRIEVE'` 로그 `detail.dropped` 에 포함.
  - (c) 응답 미사용: `detail.included` 에 있는데 응답에 반영 안 됨.
  - item의 `source.turn_no` 로 어느 발화에서 나온 기억인지 추적한다.
- 통과 기준(제안): 어려움 정답률 70% 이상, 지어냄 5% 이하. 1문항 ≈ 2%p라 기준 근처 차이는 오차로 본다.

### 리포트 표기 규칙
- `[실측]` 실제 실행 결과, `[추정]` 계산·가정, `[미검증]` 확인 안 한 것.
- 기대 정답(`expect`, 우리가 작성)과 실제 모델 응답은 다른 열에 두고, 실제 응답은 원문 그대로 인용한다.
- 성공 사례만이 아니라 실패 사례도 유형별로 원문을 싣는다.

## 10. 제출물과의 연결

- `model/bench/scenarios/*.json` 대본은 그대로 **평가자용 재현 시나리오**가 된다.
- `scripts/run-scenario.sh <서버주소> <대본>`: curl만으로 대본을 한 턴씩 보내고, 확인 질문 턴에서는 기대 정답과 실제 응답을 나란히 출력, 마지막에 비용 리포트를 출력한다.
- 평가자는 대본 없이 자유 대화도 할 수 있다(채팅앱의 `scripts/demo.sh`).

## 11. 한계

- 대본이 고정이라 실제 사용자처럼 반응하지 않는다(사용자 역할 모델은 비용·비결정성 때문에 제외).
- AI 판정은 사람 선호와 어긋날 수 있다. 사람 보정 20개로 일부만 확인한다.
- "계속 대화하고 싶은가"는 이 테스트로 증명할 수 없다. 실제 사용자 실험이 필요하다(판단 질문 4).
- 한국어 토큰 수는 토크나이저마다 다르므로 비용 비교는 실측 usage로만 한다.
- 캐시는 업체 쪽에서 보장하지 않는다(서버 사정으로 비워질 수 있음). 캐시 적중률을 함께 보고하고, 캐시 없음 기준 비용도 병기한다.
